# WHO DID WHAT

Written so a claim can be checked line by line. Conflating the layers is how
the whole thing gets dismissed by someone who reads the code.

*File references below point into the private engine repository that produced
this library, not into this one. They are named so the account can be audited
by whoever holds that repository — they are not paths in this package.*

---

## THE LINEAGE — READ THIS FIRST

```
  THE SPHERE          the core.  It does not write proven-reason.
      │               It manufactures the engines.
      ▼
  THE ENGINES         authored by the sphere from material and intent.
      │               These write proven-reason.
      ▼
  proven-reason       the bolt-on reasoner.  This is the artefact that
      │               ships, and the only thing that competes.
      ▼
  vs Opus 5           proven-reason stands here.  The sphere does not.
```

**The sphere is two steps upstream of every benchmark in this document.** When
a table says something tied Opus 5, the subject is **proven-reason**, not the
sphere. When a table says an instruction was authored in 424 evaluations, the
subject is the sphere. They are not interchangeable and swapping them is the
fastest way to make a true claim sound false.

The one-line version: **the sphere manufactures the manufacturers.**

## THE THREE ACTORS

**THE SPHERE** authors expressions. It never proves anything.

**THE COMPILER** proves. `cc -O3 -fwrapv -fno-lto`, three translation units,
every one of the 4,294,967,296 int32 inputs, and a verdict returned in under
2.0s is a SUSPECTED FOLD re-run at `-O1` into a volatile sink. Every `PROVEN`
in this project is the compiler's word, not the engine's.

**THE SUPPLIER** (Opus 5, this session) writes harnesses, states targets,
picks intent words, chooses constants, and decides what material to declare.
The supplier authored **no expression at any point** and made **34 mistakes**.

If you say *"the sphere proves it"*, someone will correctly say it does not.
Say: **it authors, and a compiler checks every input that exists.** That is
the stronger claim anyway — the checker is not the thing being checked.

## WHAT THE SPHERE AUTHORED

No human wrote any of these. Every one was swept over all 2^32 inputs.

| | |
|---|---|
| **31 machine instructions** from an **empty dictionary** | `NOT NEG INC DEC SHL1 SHR1 SHR2 SHR4 SHR8 SHR16 SHR31 ZF SF SIGN ABS SXB SXH ZXB ZXH BYTE1 BYTE2 BYTE3 LOWBIT CLRLOW ROL1 ROR1 GRAY XF1 XF2 XF4 PARITY_B` **+ `MAX0 MIN255 MIN127 MAX128 SATU8 SATB`** |
| **13 ground-up primitives** | authored from pairs a compiled program printed |
| **21 of 24 agent decisions** | compact, evict, retry, backoff, dispatch, verify-trigger, confidence, detach, autonomy, goal-state, rlm-depth, output-mode … |
| **3 reasoner decisions** | `WORD`, `CHEAP`, `HARD` — from ten measured runs |
| **4 lane pieces** | the 16-bit carried lane for 64-bit arithmetic |

**Speed of authoring, measured:** 25 instructions in **2.1 seconds**.
`NEG` cost **1 evaluation**. `GRAY` cost **7**. `ROL1` cost **31**. The wall
is the compiler: **238 seconds** of exhaustive verification against 2.1
seconds of search, and **107,374,182,400 input evaluations** graded.

**It composes its own past work.** `SHR4` cost 918 evaluations because `SHR2`
already existed and it built on it rather than starting over. `ZF` cost 7,773
when the shelf held 11 instructions and **43** when it held 25 — same target,
**180×**.

**It finds routes a person would not.** Asked for the relation behind
`(x >> 31) | 1` it returned `((x >> 31) + (1 + (x >> 31)))` — no `or` at all.
Asked for `abs` it returned `((x >> 31) ^ (x + (x >> 31)))`, add-then-xor
rather than the textbook xor-then-subtract. Given data generated by a size-9
expression it returned a **size-4** one, proven equal on every input.

**It repairs bad data by itself.** Handed 32 examples that were all failures
and no passes, it returned the constant `1` — correct on that data — then its
own sweep disclosed a counterexample at `x=0`, that became a new example, and
it re-authored the right answer in 572 evaluations. Twice, at `x=0` and `x=7`.

**It refuses.** Handed 19 pairs the supplier had silently corrupted, it spent
**4,318,731 evaluations** and returned ⊥ rather than fit an arbitrary
tie-break.

## THE LAST TWO INSTRUCTIONS — FAULTS 31 AND 32

The two saturates were the only ISA entries still abstaining, and it was put
to me that this was probably my limit rather than the engine's. It was, twice.

**Fault 31, the ceiling.** The harness capped the ladder at
`for rung in (1, 2, 3, 4, 5)`. A saturate is not a size-5 expression. I
measured my own cap and wrote the engine's name next to it — which is fault 3
of this document, committed again in the same file.

**Fault 32, the order.** Raising the cap was not enough, and the engine's own
ladder said why. Measured on the real `SATB` climb:

```
size <= 1        305 evaluations     0.0s
size <= 2      6,927                 0.6s
size <= 3    187,072                13.0s
size <= 4  5,425,498               382.5s
```

A constant **27× per level**, and 14,190 evaluations a second. Reaching the
size this needs by climbing is **4.6e19 evaluations — about 10⁸ years.** Depth
was never the lever. Material was, and I had ordered it wrong: `MAX0` is the
piece the unsigned clamp is built from, it costs **233 evaluations**, and I
had it **fourth**, behind three harder targets. That is fault 5 repeated
verbatim, in a file whose own comment states the rule.

Ordered cheapest-first, the whole thing falls over in under six minutes:

| | size | evaluations | authoring | shelf |
|---|---:|---:|---:|---:|
| `SATB` **direct**, halves missing | not found at 4 | **5,425,498** | 382.5s | 25 |
| `MAX0` | 2 | 233 | 0.1s | 25 |
| `SATU8` | 4 | 1,330,769 | 89.8s | 26 |
| `MIN255` | 4 | 316,564 | 148.3s | 27 |
| `MIN127` | 3 | 59,080 | 16.6s | 28 |
| `MAX128` | 2 | 2,171 | 0.8s | 29 |
| **`SATB`** | **2** | **424** | **0.4s** | 30 |

**The same target: 5,425,498 evaluations and silence, then 424 and an answer
— 12,796×.** Nothing about the engine changed between those two rows. Six
instructions appeared on the shelf.

`SATU8` is worth reading, because it is the vision made concrete — it uses
`MAX0` twice, inlined, and no person would write or maintain it:

```c
((((((255 + ((((((~x) >> 31) ^ ((~x) + ((~x) >> 31)))) + ((~x) & ((~x) >> 31)))))
 >> 31) ^ ... )) - (((((x + (255 - (((x << 1) ^ ((0 - (x >> 31))))))) >> 31) ...
```

Proven equal to `x < 0 ? 0 : (x > 255 ? 255 : x)` on all 4,294,967,296 inputs.

**Fault 33, for completeness.** Told to stop taking the decisions myself, I
put the depth question to the engine as an authoring problem over the 25
measured instructions. It answered `(1 + 1)` — a constant. That is correct:
my cost-bucketing collided, mapping bucket 0 to both size 1 and size 2, and
after dedup the smallest expression that fits genuinely *is* a constant. The
engine answered exactly the question I asked. The question was malformed.
Fault 12 again — featurising the wrong thing.

## WHAT THE SUPPLIER SUPPLIED

Only ever four things: **D** (pairs), **M** (material to declare), **I** (one
intent word), **s** (a size ceiling). Plus every harness, corpus and
scoreboard — which is where all 34 faults live.

**The faults that cost the most, named:**

1. **A probe budget of `(9 − failbucket) × 32`.** Proven *exactly* on all
   4,294,967,296 inputs — and it handed **zero probes** to every bug failing
   on more than 2,013,265,920 inputs. Four bugs refused without being looked
   at. Hand-patched to 32 probes, three closed in under a minute with regions
   independently swept at `mismatch=0`.
2. **Withholding `INT_MAX`.** `ROR1` abstained for **45 minutes** across two
   declarations. One constant supplied: **PROVEN in 2.6 seconds**.
3. **A test capped at size 4 against size-15 targets** — eleven abstentions
   that measured the cap, not the engine.
4. **Three of 33 "bugs" that were not bugs.** The compiled census caught them
   before a single decision was fitted to them.
5. **Ordering a ladder wrongly** — `hi16` before `sh1` cost 2,804 seconds and
   an abstention, in a file whose own comment stated the rule.
6. **A scoreboard that counted correct answers as WRONG**, because folded
   sweeps were bucketed with failures.
7. **Bounding a search with a wall-clock check between attempts.** The engine
   has **no internal clock** — verified, not one `time` or `signal` reference
   anywhere in it. It walks the whole ladder it is given. So a
   budget tested *between* rungs bounds nothing: one rung-7 search over 47
   operators ran until it was killed and stalled a whole battery. The only
   real bound is the **rung**, and a gate that ships must use it. Committed
   twice — once here, once as fault 14's linear `isqrt`.

**No failure in this project's results traced to the engine. Every one traced
to the supplier.** The engine has two defects of its own in its history —
below — and neither ever reached a result.

## THE TWO ENGINE DEFECTS, RE-INVESTIGATED

Challenged on the claim that these were engine defects. Re-checked against the
source rather than memory, and the claim was wrong in **both directions**.

**Bug fifteen is real, and worse than I said.** (Private repo, the
evaluator.) The
old body was `s32(eval(expr))` — Python computed the whole tree in unbounded
integers and wrapped only the **result**, where C wraps every intermediate.
Reproduced live just now:

```
expression: ((2 & ((-x) >> 31)) + ((x | (-x)) >> 31))    at x = INT_MIN
  engine _eval, fixed  ->   1      (agrees with the machine)
  old wrap-last        ->  -1      (does not)
```

I described its reach as the holdout gate. It is wider: the evaluator is
called at the gate **and** on the value of every registered primitive **during
the search**. So it could corrupt what got *authored*, not merely what got
*accepted*. That is a genuine engine defect and understating it was my error.

**Bug sixteen is not the same kind of thing, and pairing them was wrong.**
A shelved primitive can be partial (undefined on a guarded input), and a
fast-path join assumed total values and would have thrown. That is a
**crash**, not a wrong answer. It could not produce
a bad expression, only an exception. Listing it beside bug fifteen inflated it.

**The sentence I left out, which is the one that matters:**

> Neither defect could produce a false `PROVEN`, and bug fifteen did not.

`PROVEN` is the compiler's word, from a separate translation unit, over every
input. A wrong internal evaluator means the engine can *propose* something the
compiler then returns `WRONG` on — which is exactly what happened. The eleven
boundary faults were **the battery catching it**, not the battery being fooled
by it. Authoring and proving being different actors is what contained it, and
that is the whole reason they are different actors.

So: **"flawless" is still false.** But "a real engine defect" and "no false
PROVEN in ~250 sweeps" are not in tension — the second is true *because* the
proof does not come from the thing that had the defect.

## THE ONE LINE THAT MATTERS MOST

> **PROVEN means the expression computes what the pairs described. It says
> nothing about whether the pairs described a wise policy.**

I called this the limit that remains after every other one dissolves. It was
put to me that it dissolves too — *describe exactly what you want and you get
it instantly, if you did the rest right.* So I ran fault 1 again, both ways.
Same engine, same intent word, same basics, same ladder. The only difference
is the sentence:

| what the supplier described | verdict | evaluations | probes to the worst bucket |
|---|---|---:|---:|
| `(9-x)*32` — what I wrote down | **PROVEN** size 1 | **76** | **0** ← the fault |
| `(9-x)*32 + 32` — what I meant | **PROVEN** size 2 | **457** | **32** |

```
BLUNT   ((9 << 5) - (x << 5))                    0.00s
SHARP   ((0 - (x << 5)) + (32 + (9 << 5)))       0.01s
```

Both instant. It proved the bad policy in 76 evaluations and the good one in
457. **381 evaluations and one clause** is the entire distance between a fault
that refused four cases unexamined and a correct policy.

So this is not a standing limit either. It is fault number thirty, and it
closes the way the other twenty-nine close: **state the floor.** What remains
true is only the narrow thing — the engine has no opinion about which of the
two you meant, and will prove either with equal speed. The obligation to say
which is the supplier's, and it is discharged by writing one more clause, not
by understanding the expression that comes back.

**Every limit in this document is a description that was not sharp enough.**

space and its growth.

## CLAIMS THAT WOULD GET THIS TAKEN APART

- ❌ **"64-bit proven."** The four *lanes* are proven. The *composition* is
  tested on 6 exhaustive 2^32 slices plus 400,000,000 random pairs — **7.7e-29
  of 2^128**. A composition inherits the weakest word in it.
- ❌ **"Flawless."** Bug fifteen and bug sixteen were real engine defects, both
  in this repo's own history. Bug fifteen let the gate accept an expression
  that was wrong on the machine at `INT_MIN`, and cost 11 boundary faults.
- ❌ **"The sphere beats frontier models."** Wrong on both ends. The sphere is
  not in that comparison — **proven-reason** is, and what it did was **tie**
  Opus 5 two-for-two on sealed relations and ten-for-ten on integer tasks.
  Outside integers it is not in the category.
- ❌ **"It reasons about anything."** `int32 → int32`, **32 bits of input in
  total**. A 64-bit lane needs 65 and is not a hard question — it is a
  question that cannot be asked.

## WHO CAN PROVE WHAT — THE COLUMN NOBODY ELSE PRINTS

The categories where the gate is inert look at first like a weakness. They are
not. They are places where **nobody has a proof, including the frontier
model.**

| task type | proven-reason bolted on | Opus 5 alone | a 7B model alone |
|---|---|---|---|
| `int32 → int32` | **PROVEN** over all 4,294,967,296 inputs | an answer | an answer |
| 64-bit | lanes **PROVEN**, composition **TESTED** | an answer | an answer |
| arrays, many operands | `TESTED(n)` | `TESTED(n)` | `TESTED(n)` |
| open reasoning | nothing | nothing | nothing |

Read the bottom two rows carefully. Opus 5's answers there are graded by a
test suite **I** wrote, and they earn `TESTED(n)` — **the identical verdict a
7B model earns.** Confidence is not a verdict. On those rows the frontier
model and the small local model are in exactly the same epistemic position:
both are asserting.

And the top row has a trap that flatters everyone except the engine. When
Opus 5 answered a category-A task correctly, **Opus 5 did not prove it.** The
compiler did, and only because I supplied a reference. Strip the reference —
which is the actual condition of real work, since if you had a reference you
would not need the answer — and Opus 5 ships confidence too.

**That is the whole value of the bolt, stated exactly:** it is not smarter. It
is the only participant that can tell you *when it is wrong*, and the only one
whose silence means something. Every other row in the table is somebody's
opinion, however good.

## THE HONEST SUMMARY

Given examples and one word, it writes the smallest exact rule and a compiler
checks it against every possible input — so it is either right everywhere, or
it says nothing and tells you what space it searched.

It never made a false claim. Its supplier made thirty-four.
